# Authentication migration

The native API now mounts registration, login, logout, hosted password recovery
and browser handoff, instance discovery, self-host setup/enrollment/renewal,
and hosted self-host entitlement proof issuance
under the bare, `/api`, and `/v1` aliases. Go remains the deployed owner.
This is a tested subset of authentication, not approval to switch the API.

## Preserved contracts

- Existing users, license IDs, bcrypt password hashes and SHA-256 session hashes
  are read directly; there is no password or account conversion.
- Password compatibility fixtures are generated by Go and Node and consumed by
  both implementations. They cover ASCII, Unicode, embedded NUL, and bcrypt's
  72-byte comparison boundary. New passwords longer than 72 UTF-8 bytes reject.
- Registration creates the account, Basic license and 30-day session in one
  transaction. Login returns the existing `user_id`, `name`, `username`, `email`
  and `token` shape. Explicit bearer credentials take precedence over the
  `misty_session` cookie. Downloaded-app sessions are never account credentials.
- Session cookies are host-only, HttpOnly and path `/`; TLS and trusted proxy
  settings determine Secure. The existing SameSite selection is preserved.
- Self-hosted login verifies a subject-bound Ed25519 entitlement proof and updates
  the cached expiry before session creation. Public registration stays closed.
- Handoff links last 60 seconds and issue 12-hour browser sessions. Redirects are
  restricted to the existing account-settings paths. Invalid/expired/replayed
  links redirect to settings without issuing a new session.
- Recovery keeps `/auth/forgot`, `/auth/reset/start`, `/auth/reset/validate` and
  `/auth/reset`, the `misty_reset_token` HttpOnly cookie and a 15-minute token
  lifetime. Unexpired Go-issued reset tokens remain redeemable.

## Transaction and request boundaries

Password work uses asynchronous bcrypt with bounded concurrency and queue length.
Login rechecks the verified hash and active account under a row lock before
creating a session. A concurrent password change or deactivation cannot mint a
session using stale account state.

Handoff minting rechecks a live account session under locks. Redemption consumes
the token and inserts its replacement session in one transaction; failed inserts
roll back token consumption. Concurrent redemptions issue exactly one session.
Expired links and links for deactivated accounts are consumed without a session.
The destination never contains the handoff token, and responses set no-store and
no-referrer. Handoff repositories require the existing service RLS mode but still
run as the restricted application PostgreSQL role.

Authentication bodies are limited to 8 KiB without imposing that limit on other
domain routers. Aliases share login/register/handoff IP rate limits. Forwarding
headers are used only when enabled and received from a trusted peer; malformed
proxy configuration fails startup. Explicitly allowed browser and Tauri origins
are supported. Cross-site mutations from untrusted origins are rejected before
dispatch. This origin rejection is an intentional security improvement over the
old permissive request handling.

## Evidence

The restricted-role authentication HTTP integration suite has 12 tests covering
registration races, password-change races, cookie/session expiry and revocation,
app-token separation, self-host proof validation, origin/body/rate limits,
handoff replay races, failed-insert rollback, deactivated accounts and safe
redirects. Unit and Go fixtures verify hashing and configuration boundaries.
The recovery suite has 13 additional PostgreSQL/HTTP tests, including concurrent
resets, rollback after revocation failure, old Go reset tokens, durable enqueue
failure, retries after restart/key rotation, lost worker leases, superseded jobs
and prevention of consumed-token resurrection. Mailjet tests inspect the real
request shape with an injected transport; they send no email.
The Linux API image starts with the native bcrypt binding and remains unready
while migration parity is incomplete.

## Recovery delivery and operation

Forgot-password requests commit a job before returning 202. Every address follows
the same enqueue path; account lookup and Mailjet delivery occur in the polling
worker after the request. Unknown and deactivated accounts receive no mail.
An enqueue failure returns 503 for any address instead of falsely acknowledging
work. Provider errors never change the public response or expose addresses,
credentials, response bodies or reset links in logs.

Each job has a fenced 60-second lease and bounded retry backoff. Token generation
uses HMAC-SHA-256 with a private 32-byte key, a domain label, random job UUID and
normalized email. The job records its key ID, not the key or redeemable token.
Retries after a crash or lost acknowledgement use the same link; a consumed or
replaced token is never reissued. Duplicate delivery is possible after an ambiguous
provider acknowledgement, but the same single-use credential is delivered.
Requests have a database sequence so equal timestamps cannot confuse which
request supersedes another. Indexed claims examine pending and expired leases
separately. Queue records expire with the request after 15 minutes.

Reset locks the account before its token and credential rows. It changes the
password, consumes the reset token, revokes account/app sessions and handoffs,
and supersedes outstanding recovery jobs in one transaction. This deliberately
strengthens the Go reset behavior, which did not revoke those credentials.
Cleanup deletes expired session/reset/handoff rows in independent batches of at
most 500 per table, skipping locked rows. Delivery-job history is retained until
24 hours after expiry and then cleaned in the same bounded manner.

Hosted production startup requires `MAILJET_API_KEY`, `MAILJET_SECRET_KEY`,
`MAILJET_FROM_EMAIL` and `AUTH_RECOVERY_TOKEN_KEYS_FILE`. The sender follows the
[Mailjet Send API v3.1 contract](https://dev.mailjet.com/docs/email-api/send-api-v31/send-basic-email)
with HTTPS, no redirects, a 10-second deadline, at most 16 concurrent sends and a
16 KiB response limit. Optional `MAILJET_FROM_NAME` and `MAILJET_API_BASE_URL`
retain their existing names. Development without recovery configuration returns
503 for recovery requests; it never prints reset links to application logs.
Self-hosted deployment instead returns 501 for hosted recovery and handoff paths,
matching the existing feature gate, and requires neither Mailjet nor recovery
token keys. Its password recovery remains a local administration operation.

The recovery key file is private JSON with shape
`{"active":"key-id","keys":[{"id":"key-id","key":"<base64 of 32 random bytes>"}]}`.
Provision it through the deployment's secret store and mount it read-only for
the application user. Keep old keys available while unexpired jobs reference
them; changing the active ID affects new jobs only. Back up the key ring with the
deployment's secrets, separately from database backups. The image smoke creates
temporary test keys and uses an isolated network with fake provider credentials.

`PASSWORD_RESET_START_URL` and `PASSWORD_RESET_URL` retain their existing names
and development defaults, including the reset-page fragment. Set both to deployed
URLs before cutover. Verify real delivery with a controlled recipient and confirm
sender activation, browser cookie behavior, queue backlog alerts and key rotation
in staging before ownership changes. These external checks are not yet complete.

Migration `20261129000000_normalized_account_email.sql` makes email uniqueness
match the existing case-insensitive login lookup and adds its lookup index.
Preflight `SELECT COUNT(*) FROM (SELECT LOWER(email) FROM users GROUP BY LOWER(email)
HAVING COUNT(*)>1) collisions` must return zero. Existing collisions stop the
migration; preserve both account IDs and resolve ownership explicitly. The index
build needs the migration maintenance window; do not run competing Go/native
writers or migration runners during cutover.

## Outstanding ownership gates

The `/me` summary, avatars and password-confirmed account export are native; see
`account-summary-cutover.md`, `avatars-cutover.md` and `account-export-cutover.md`.
Account deletion, global abuse policy and its shared persistence, and full
authentication telemetry remain incomplete. Full domain authorization
must use the account/app distinction explicitly when native domain routers mount.

Keep the lock order account first, then credential rows when adding those flows.
Runtime grants must cover the recovery job table and its identity sequence, while
keeping the API role out of the billing schema. Account deletion must also
handle pending recovery metadata by normalized email before final cutover.

Provision runtime grants and verify hosted and self-hosted reverse-proxy/browser
flows before changing ownership. `AUTH_HANDOFF_START_URL` and `MISTY_WEBSITE_URL`
retain their existing names and development defaults. Native validation rejects
credentials/query/fragment in those URLs and requires the website to be an
origin. Production must supply the deployed API and website origins explicitly.
No live authentication endpoint, production data, email or deployment was changed.

## Native self-host boundary

Instance discovery preserves the database-backed server ID, display name,
protocol version 1, registration mode and capability descriptors. Bootstrap,
enrollment, administrator invitation/revocation and proof renewal have native
routers and repositories. Cached entitlement expiry/disablement is checked for
both full-account and downloaded-app sessions. Renewal and logout remain usable
after expiry; an app token never gains administrator or renewal powers.

Bootstrap issuance and consumption share an advisory lock, so two different
valid bootstrap tokens cannot create two first administrators. Account, license,
self-host binding, token consumption and session insertion commit together.
The creation transaction temporarily uses the existing registration RLS identity
for the user insert and switches back to service mode for the authorized binding.
No RLS policy is relaxed. Go's older self-host path assumed service mode could
insert users; native tests run under a restricted role and cover the real policy.
Do not overlap old and new bootstrap writers at cutover: the Go path does not
participate in the new advisory lock.

Nine PostgreSQL/HTTP/CLI tests verify durable identity, bootstrap races and
rollback, single-use/revoked invitations, subject uniqueness, admin restrictions,
cached expiry and renewal, app-token boundaries, hosted-only feature denial,
local admin password/disable operations and stdin handling. Isolated Linux image
smoke now covers both hosted and self-hosted API startup explicitly.

Native administration is available as `npm run admin -- bootstrap-token`,
`npm run admin -- reset-password --email EMAIL`, and
`npm run admin -- disable-account --email EMAIL`. The built image equivalent is
`node dist/apps/api/src/admin.js` followed by the same arguments. Commands require
`MISTY_DEPLOYMENT_MODE=self_hosted` and explicit database configuration. Passwords
come from stdin and are not echoed by the interactive terminal reader or included
in command arguments/output. Bootstrap intentionally prints its new one-time token.
Password reset and disabling revoke full-account/app sessions, reset links and
handoffs; disabling also revokes outstanding invitations issued by that account.

The existing Go `misty-admin` binary and its CLI/container wiring have not yet
been removed. Hosted proof issuance cutover, native domain dispatch/feature checks,
collaboration protocol integration and real desktop/self-host deployment parity
remain ownership gates. These local tests do not establish full self-host parity.

## Hosted self-host proof issuance

The hosted API now implements `POST /billing/self-host-entitlement` under all
three aliases. This remains an account-only route, outside the public SDK.
It accepts a live trial or an active/trialing payment projection with an unexpired
paid period. The API reads only its own license/projection tables under user RLS;
it neither queries Stripe nor reads the payments schema. Lifetime grants alone
remain ineligible, matching Go. Online subscription reconciliation grace does
not extend offline proof issuance beyond the paid period.

The signer preserves `MISTY_SELF_HOST_ENTITLEMENT_PRIVATE_KEY` (base64 DER PKCS8
Ed25519), `MISTY_SELF_HOST_ENTITLEMENT_KEY_ID`, and
`MISTY_SELF_HOST_ENTITLEMENT_SUBJECT_SECRET` (base64, at least 32 bytes).
Preserve the existing subject secret exactly: account bindings depend on its
HMAC-SHA-256 of the existing user ID. Signing keys may rotate with their public
verification keys; rotating the subject secret needs an explicit account-binding
migration. Missing signing configuration yields 503 for eligible accounts;
partial/invalid configuration fails hosted startup without exposing its values.
Self-hosted instances load no signing secrets.

Proofs preserve issuer, audience, schema, unique token IDs and stable opaque
subjects. Expiry is capped at seven days and the eligibility deadline, rounded to
JWT whole seconds. Responses are no-store; aliases share a bounded IP rate limit.
Four unit tests include fixture verification in both runtimes, signing-key
rotation, bounded expiry and malformed configuration. Six restricted PostgreSQL
HTTP tests cover eligibility/status boundaries, all aliases, account/app and RLS
separation, origin checks, missing/broken signers and rate limits. The Go
compatibility test verifies Node-issued signatures, stable HMAC subjects and
exact expiry using public test-only fixtures.

Before routing this endpoint to Hono, backfill and reconcile every existing paid
subscription into the API projection and verify representative accounts against
Go. A missing projection does not read through to legacy Stripe tables; without
an eligible trial it denies issuance. The legacy null-period subscription case
also requires reconciliation to a real billing period before cutover. Provision
the unchanged signing/subject secrets, confirm deployed self-host clients trust
the active public key, and rehearse renewal across the ownership switch. These
deployment/data gates remain open; local fixture tests do not satisfy them.

## Account profile and preferences

Native `PUT /me/profile`, `PUT /me/device`, `GET/PUT /me/settings` and
`PUT /me/telemetry` now mount under all three aliases. They require full active
account sessions and operate under user RLS. Name trimming, device whitespace,
the success response and preference field names retain their Go behavior.
Settings PUT replaces all three booleans; omitted/null flags default to false.
Telemetry updates only analytics/error reporting and preserves email preferences.
Bodies are strict single JSON objects capped at 8 KiB on these routes only.

Writes recheck active account state in their transaction; the device update locks
the account before its license. No identity, email, username or license tier can be
changed through these request schemas. Four database HTTP tests cover aliases,
replacement semantics, cross-account isolation, untrusted origins, malformed
bodies, app-token rejection and deactivated-account writes. Native authentication
errors use the existing native `not_authenticated` JSON response rather than
the Go preference handlers' plain-text error. The main `/me` response still needs
the payment-status/trial-eligibility integration before it can preserve the current
contract without reading Stripe-owned tables.
